# 核心工作与输出风格约束

**常驻硬约束（跨新会话、换模型、其他工作树生效）**：
- 本项目一切任务（包括新会话、切换模型、进入其他 `.worktrees/*` 工作树）开工前，必须先读取并遵守权威项目风格文件 [ASTRA_MODEL_STYLE.md](ASTRA_MODEL_STYLE.md)（v1.3），交付前完成三句自检，不等待用户提醒。
- **工程通用四原则**：（1）以完整流程可用为先：每道硬门说清防止的具体错误，纯格式/展示/辅助问题记诊断放行；（2）同一事实只维护一处、同一规则只设一个负责入口：删除合并重复校验与恢复；（3）局部故障就地处理：保留已有有效结果，恢复从已有结果接续、禁止重做已成功步骤；（4）用真实入口和实际边界验收：隔离产物但保持调用与服务身份真实，写清实际走到哪一步及尚需线上实证之处。
- **交付前自问三句**：① 删掉这道限制会出什么具体错误？② 这一处失败会不会抹掉前面已经有效的结果？③ 使用者现在能走到哪一步？

**目的**：在保留深度推理与全局洞察力的同时，强制保持干净、高效、可决策，严控无效 Token 消耗。  
**适用范围**：所有项目梳理、规则设计、数据提取、牌面构建、协议编写、文档输出任务。（注：直接编写可执行代码文件时需保持代码完整，禁止在代码中使用省略占位）。  
**优先级**：本文件中的风格约束高于「完整性」「可审计性」「防御性」的默认倾向。

## 1. 核心原则
1. **决策可用性优先于审计完整性**：输出首先要能被下游（尤其是 AI 牌手或执行模块）直接使用并做出判断。不能为了严密而牺牲可操作性。
2. **先给能用的结果，再补技术细节**：任何任务都必须先产出面向最终使用者的精简版本，技术协议、哈希、Schema、边界情况放在后面或按需附录。
3. **默认积极，而非默认保守**：若信息可通过本地文件检索确认，先检索再结论；在已有信息基本充分时，必须做出明确判断与收敛方案。只有在关键条件真正冲突或两侧都不可用时，才转向拒绝或未知。长期不作为不是严谨，而是回避。
4. **聪明用在收束上，而不是用在展开上**：内部推理（Thinking）应优先用于识别什么是主干、什么可以省略、如何降维，而不是在输出中穷尽所有边界情况和未知项。

## 2. 输出纪律
- **长度控制**：核心内容优先控制在能快速阅读和推理的篇幅内，严禁长篇大论铺垫。
- **聚合优于原子化**：能按结构、位置、关系汇总描述的，不要拆成逐条细项罗列。
- **短句优于长模板**：现象和结论尽量用直接、具体的短句表达，避免重复句式堆砌。
- **省略优于占位**：无法干净使用或对当前决策无增量的信息，直接省略。不要用大量 “Unknown”“待确认”“关系未知” 占据主体位置。
- **Unknown 的使用限制**：仅在该缺口会实质性阻止对主要选项做出判断时，才显式标出并说明是否阻塞决策。禁止系统性罗列未知项。

## 3. 禁止的默认行为
- 禁止为了防止理论上的偏见或泄漏，把输出做成重型协议或过度封闭的 Schema。
- 禁止把「尚未观测到」一律上升为需要显式声明的未知并占据核心篇幅。
- 禁止在可以做出有条件判断时，仍倾向于输出保守的拒绝或未知。
- 禁止用完整性、可追溯性、防风险作为拒绝降维和精简的理由。
- 禁止把单一任务扩展成完整的审计系统或生产级框架，除非明确要求。
