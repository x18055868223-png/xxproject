# 信号审计更新部署规范 v1.0

## 1. 目的与适用范围

本规范适用于 `deploy/signal_audit/`、`tools/signal_llm_review*.py`、materializer、systemd 资产、LLM Prompt、sidecar schema 和信号审计前端的后续功能迭代、推送与服务器更新。目标是把发布变成可重复、可停止、可回滚的标准流程，禁止把生产服务器当作开发调试环境。

FMZ producer、GEX 服务或交易执行层不因信号审计发布而自动进入范围。涉及这些资产时，必须另行执行三层版本一致性与各自的安全门禁。

## 2. 不可绕过的发布原则

1. `xxproject` 是项目权威仓库；提交、推送和部署前必须核对 remote、分支和目标提交哈希。
2. LLM 始终是 `AUDIT_ONLY`，不得改变 producer direction、confidence、blocking、trade permission 或 execution permission。
3. 密钥只存在于环境变量或服务器 `/etc/signal-audit/llm.env`，不得出现在命令回显、日志、diff、sidecar、截图或项目记忆中。
4. 本地测试通过不等于部署成功；部署脚本成功不等于真实调用成功；systemd service 成功不等于前端卡片完整。每一层必须分别给出证据。
5. 前端改动必须先完成本地桌面与移动浏览器检查，并经过用户的“当前本地页面可推送”门禁，才允许提交、推送和部署。
6. 默认安装不得自动启用 LLM timer。只有 canary、严格自检、物化和外网页面验收全部通过后才能启用。
7. 任一强制验收失败都立即停止，不得通过连续 API 重试、放松 validator、跳过自检或直接启动 timer 来掩盖问题。

## 3. 标准发布流水线

### 阶段 A：变更前基线

- 阅读 `AGENTS.md`、`PROJECT_MEMORY.md` 和本规范。
- 确认工作树、分支、`xxproject` remote、HEAD、dirty files 和服务器当前提交。
- 记录本次明确范围、禁止触碰范围、代表卡 ID、预期 schema/provider/model/prompt 版本。
- 读取服务器 timer、service、usage ledger 和最新真实卡状态；禁止先写服务器再调查。

### 阶段 B：本地实现与最小充分测试

- Prompt/schema/validator/entrypoint/materializer/frontend 必须按真实调用链一起审查。
- 至少覆盖正常输出、空正文、非法 JSON、缺字段、语义冲突、硬阻断、旧卡兼容、冷却/终止、每日额度和敏感信息脱敏。
- 前端至少覆盖最高辅助交易决策、LLM 复核、24 小时报告、原始追溯、长中文、旧卡和错误卡；禁止 enum、evidence ID、`undefined`、`[object Object]` 泄漏。
- 运行相关 Python 测试、语法检查和 deploy asset 测试；保存命令与结果，不得声称未执行的测试通过。

### 阶段 C：真实 API canary

- 使用一张代表性模拟或复制卡，在隔离临时目录执行真实 DeepSeek 调用；不得直接写生产 sidecar。
- 主信号验证 blind-first 与 reconciliation 的实际调用数、profile、usage、schema、policy validation 和完整报告。
- 真实响应失败时按失败类型处理，不得盲目重打：
  - `EMPTY_CONTENT` 且存在 reasoning：只允许一次 reconciliation recovery；仍失败则冷却到下个允许窗口。
  - JSON 截断或非法 JSON：不得立即重打；先修正输出预算、Prompt 或解析边界并重新跑本地测试。
  - schema/语义缺字段：只允许显式、受限、可审计且最终仍通过完整 validator 的本地安全修复；不能安全修复则记录失败。
  - 401/403、无效模型、缺配置：立即终止，不重试。
- canary 不通过时禁止推送、部署和启用 timer。

### 阶段 D：本地页面验收

- 用 canary 真实 sidecar 物化仓库外临时站点。
- 桌面 1440×900 与移动 390×844 均检查：层级、溢出、长段落、点位来源、旧卡兼容和原始追溯。
- 确认最高辅助交易决策、未来 24 小时第一性推断、LLM 复核意见均可见，且 producer hard block 未被绕过。
- 用户确认“当前本地页面可推送”后才进入阶段 E。

### 阶段 E：提交与推送

- 只提交已验证且在范围内的文件；再次检查 diff 和 secrets。
- 推送到 `xxproject` 的目标分支，记录不可变 commit SHA。
- 不得以分支名或 `FETCH_HEAD` 猜测部署版本；服务器必须验证拉取到的 SHA 与目标完全相等。

### 阶段 F：服务器安全安装

- 停止 LLM timer/service，保留 materialized cards、sidecar、ledger、state 和 `/etc/signal-audit/llm.env`。
- 安装脚本使用安全默认值：不自动运行初始 LLM、不自动启用 timer、不覆盖运行数据。
- 核对安装后的脚本、systemd unit、timeout、provider/model/prompt/schema 与目标提交。
- 失败 trap 必须让 LLM timer 保持关闭，并输出单一部署日志位置和退出码。

### 阶段 G：服务器 canary 与生产验收

- 在服务器隔离目录先运行 canary，不写生产 sidecar；通过后才允许针对明确 card ID 做一次生产复核。
- 严格自检至少要求：LLM、integrated advisory、transition、materialized passthrough、session context、provider/model/prompt/schema 全部通过。
- 运行 materializer 并核对目标卡 JSON 确实包含 OK sidecar、24 小时报告与 policy validation。
- 启用 timer 后检查 timer active、service 无失败循环、每日 HTTP ledger 未越界。
- 从外部 URL 打开目标卡，桌面与移动检查最高辅助交易决策、未来 24 小时第一性推断、LLM 复核、无横向溢出和无对象字符串泄漏。

### 阶段 H：关闭与证据

- 最终记录：commit SHA、测试、canary 调用数、严格自检汇总、timer 状态、ledger 用量、目标卡 ID、外网页面结果。
- 删除本地和服务器临时脚本、临时站点与临时 SSH 凭据；不删除发布证据日志和生产历史 sidecar。
- 检查工作树干净，并更新本规范与 `PROJECT_MEMORY.md` 中经过验证、可复用的规则。

## 4. 失败状态机与重试预算

- 网络瞬断、408、429、500/502/503/504 且短 `Retry-After`：同一逻辑调用最多两次 HTTP 尝试。
- 完整超时、空正文、非法 JSON、本地验证失败：不做即时同型重打。
- 记录级冷却为 2、5、15 分钟；第四轮后终止，只有 packet hash 改变或显式人工 retry 才重置。
- 显式 retry 不能抹掉可恢复的 reconciliation 上下文；能单调用恢复时不得重新执行 blind + reconciliation 双调用。
- 北京时间每日 HTTP 硬上限为 60；额度不足时 fail closed 到次日。任何部署/调试操作都必须先读取剩余额度。
- cooling/terminal 错误不得占用正常新卡的批次名额；坏卡不能造成队列饥饿。

## 5. 回滚与停止条件

出现以下任一情况，保持 LLM timer 关闭并回滚到上一已验证提交或保留上一份公开静态输出：

- provider/model/prompt/schema 与发布目标不一致；
- canary 或严格 validator 未通过；
- hard block 被绕过或出现交易授权；
- 真实卡缺最高辅助交易决策、24 小时报告或 LLM 复核；
- materializer 覆盖/丢失历史卡；
- 页面溢出、空白、关键块消失或泄漏机器对象；
- service 失败循环、timer 重入、ledger 越界或密钥泄漏。

回滚只替换版本化代码和静态资产，不回滚或覆盖服务器本地密钥、sidecar、ledger、状态和 FMZ 源 JSONL。

## 6. 规范维护规则

每次功能迭代、推送或服务器更新完成时，负责人必须同时检查本规范和 `PROJECT_MEMORY.md`：

- 新增了稳定、可复用的发布门禁或故障分类时，更新两者；
- 只属于单次事故的日志、卡 ID、临时目录、主机凭据和猜测不得写入长期记忆；
- 规范修改与实现修改在同一分支评审和推送；
- 若流程与代码不一致，发布暂停，先修正规范或代码再继续。

## 7. LLM 重试轮次与人读输出规范

- 显式 `--retry-id` 是一次新的记录级重试轮次。新轮次首次失败必须从 `record_retry_count=1` 重新计数；相同 packet 的旧普通 `VALIDATION_ERROR` 或旧普通终止记录不得污染新轮次。`FATAL_AUTH`、`FATAL_CONFIG` 与 `RECONCILIATION_EMPTY_CONTENT_RECOVERY_EXHAUSTED` 仍跨轮次保持终止，除非配置或 packet 发生可证明的变化。
- 同一卡同一 packet 存在已校验 blind 上下文时，人工重试 reconciliation 阶段的 `EMPTY_CONTENT`、`INVALID_JSON` 或 `VALIDATION_ERROR` 应优先复用该上下文，只发起一次 reconciliation 调用；不得为修复第二阶段格式问题重新消耗 blind 调用。
- 服务器金丝雀必须把生产 main/transition sidecar 复制到隔离目录后再运行；main 隔离副本须剔除目标卡旧 OK 行但保留其失败/blind 恢复历史，再对目标卡显式开启新重试轮次，保证本轮产生新结果且不重复已有 blind；已完成的 transition 保留并复用。只有隔离结果、严格自检和物化全部通过后，才可把目标卡的唯一新 OK 结果原子合并回生产 sidecar。
- 人读字段禁止出现字段路径、`KEY=VALUE`、JSON 布尔值或机器枚举串。Prompt 负责要求自然中文；entrypoint 只对已知、安全、机械可翻译的表达做受限修复；任何未知原始字段语法继续由 core validator 拒绝，不得直接进入生产 sidecar。
- 模型缺失 `containment_assessment` 或 `premium_selling_fit` 时，只允许补成 `UNABLE_TO_JUDGE` 的本地安全值，并使任何价差复核建议降级为 `NO_TRADE`；不得猜测为适配或成立。
- 最高辅助决策中的墙位距离由本地代码从同一 packet 的现价、`call_wall` 与 `put_wall` 确定性计算。文案只解释现价处于两墙之间或墙外、到上下墙的相对距离，并明确不单独决定方向或辅助建议；不得依赖模型自行计算，也不得转写成行权价或订单参数。
- 发布验收必须同时覆盖：旧终止记录后的新重试轮次、单调用 reconciliation 恢复、缺字段安全降级、原始字段语法拒绝、墙位距离算术、最新默认卡渲染和至少两张最近卡的真实 sidecar 状态。
