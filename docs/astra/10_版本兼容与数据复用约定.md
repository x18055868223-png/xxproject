## 2. 数据由谁负责，后续复用什么

| 资产 | 权威来源与用途 | 升级时处理 |
| --- | --- | --- |
| FMZ原始审计JSONL | producer的身份、时点、原始因子、阻断及完整性记录 | 保留原文。历史卡没有原生四态就仍没有，不把离线推导写回原生记录 |
| 原生四态 | producer在计算完整性hash之前写入 | 保留来源、支持/反对/冲突/未知；不让LLM覆盖 |
| v2事实包 | 当前卡事实、有效时效和可核验前卡变化的专用投影 | 衍生量继承来源；不把旧置信、耐用总分或旧结论重新喂给模型 |
| LLM sidecar | 同次评审的原始结果与本地校验产物 | 保留旧协议记录、原返回、错误及未采纳部分；不按等级挑选结果 |
| 持久尝试目录与原响应 | sidecar旁的 .v2_attempts 目录，包括固定事实包、尝试计数与responses | 与sidecar一并备份、迁移、恢复；不为清理冗余而删除 |
| 每日调用预算 | usage ledger及运行锁 | 延续已有额度与互斥；升级或重启不清零预算 |
| 本地变化台账与状态 | materializer根据前后原始卡生成 | 保留；变化比较失败只关闭依赖变化的判断，当前截面仍可读 |
| signal_cards、manifest及fallback | materializer生成的阅读投影 | 可从同一原始数据和sidecar重建；代码安装保护已有整个卡目录，不能用包内样例覆盖真实卡 |
| Astra与原版快照 | 理论裁定、版本对应、回退和验收依据 | 保留历史，更新当前入口；模拟卡不进入生产数据或真实统计 |

页面不自行计算另一套等级。列表摘要包含输入包与完整评审结果的摘要hash，详情使用同一结果；不一致时停止显示有效评级。市场数值和证据原文留在完整审计下载中，普通页面使用中文解释。

## 3. 新旧记录怎样相处

- 旧1.x评审继续走历史阅读，不自动改成总体证据等级，不混入新版B及以上或A/S筛选。
- 当前2.0.0输出显式支持Prompt2.0.0和2.0.1。旧Prompt没有价格倾向对象时显示历史缺口，不凭页面推导一个模型结论。
- 同一卡已有新版总体证据结果时，后来追加的旧协议不能静默把它降回旧行动评级；同协议仍按记录更新顺序处理，随后执行来源、引用和行动边界校验。原sidecar文件不改写。
- 未支持的新协议不能猜字段、沿用旧等级或绕过校验。保留原记录，给出可读的未评级结果；增加协议支持必须连同输入、校验器、materializer、页面和测试一起实现。
- producer新字段可加到原始归档，不代表能直接作为独立证据。接入事实包时要声明来源、单位、观察窗、时效和同源依赖。
- 当前事实重算与冻结评审事实采用严格比对。未来修改事实名称、单位或构造语义，可能使旧评审不再匹配。应先用旧卡验证：匹配则复用；不匹配则保留原文并明确未评级，不自动重跑模型、不偷偷回填为原生。
- 跨品种、跨策略版本、缺来源hash或前后时间异常，不进行变化归因。不能把换版造成的字段变化解释成市场变化。

这套兼容不承诺“未来任意schema都能直接运行”。它保证升级遇到不能解释的数据时显式暴露缺口，避免以看似正常的旧结论掩盖不兼容。

## 4. 调用与缓存不能因升级重复花费

2026-09-09部署前实际发现：旧流程有30张失败或没有有效评审的历史卡，单纯跳过OK/PARTIAL并不能保证“不自动重评历史”。升级时把截止快照中的全部211张真实历史卡ID冻结为独立排除清单，通过`LLM_AUTOMATIC_EXCLUSIONS`配置到自动runner。清单协议为`signal_review_automatic_exclusions@1.0.0`，包含`card_ids`、来源文件SHA和生成时点；后续部署保留该清单，不能每轮定时重建而把新卡排除。自动跳过不写入伪造sidecar、不消耗HTTP额度。显式隔离研究可通过`--only-card-id`选择旧卡，仍遵守既有结果和持久额度。已配置的清单缺失、损坏或协议错误时，在请求API前停止，不能当空清单继续调用。清单与sidecar、预算和尝试记录一起备份、迁移。

正常新卡一次DeepSeek综合评审，传输恢复与格式恢复共用最多两次HTTP尝试。尝试先持久化，再发请求；定时轮次和进程重启不能重新获得额度。引用、事实或权限问题不通过重试换答案。

当前状态按卡、Prompt、模式、模型定位，状态中保存固定事实包及其hash。后到的变化或无关字段不会使同卡重新评级；已完成的旧卡默认跳过。当前还显式识别Prompt2.0.0的持久状态，恢复sidecar时复用原结果。

**修改Prompt或输入构造器不等于授权重评历史卡。** 后续若需离线研究，使用隔离输入副本、独立sidecar/尝试目录与明确的请求预算，保存原版本结果，注明离线重评。不得删除现有state或改卡ID来规避原卡额度。模型变更也需要单独核对缓存与迁移测试。

## 5. 以后怎样升级和回退

1. 从本分支完整资产树继续开发，先核对xxproject远端、当前工作树、用户可见FMZ文件和服务器最新真实卡。不要运行从旧opus基底重拼信号交付物的历史脚本。
2. 更新前保留原始JSONL、sidecar、.v2_attempts及responses、预算、变化状态和当前阅读投影。凭据保持在原环境配置中，不放入Git或Astra。
3. 用仓库当前package脚本打包。包必须同时包含HTML、JS、VERSION.json、统一入口和三个v2模块；安装器对已有signal_cards目录整体保护，即使index.json暂缺也不例外。
4. 升级沿用现有配置，但先核对provider、base URL、model。当前自动路径为DeepSeek；历史Gemini配置不能仅因环境文件仍在就当成兼容。不要覆盖凭据或依赖旧的blind/24小时报告变量恢复已退出的调用。
5. 用隔离目录物化旧卡与新卡，确认列表/详情一致、旧协议不升级、未知协议未评级、阻断不变、失败独立保留。随后审阅页面。新的页面变更仍需用户确认可推送，当前授权仅覆盖本次定稿及兼容修复。
6. 正式部署时另核对Git提交、FMZ候选内部版本、最新真实卡策略及schema。本地通过不能替代真实API、FMZ或生产采样。
7. 回退时成套回退HTML、JS、版本文件及相应工具，保留所有数据和调用状态。旧工具不保证读懂新sidecar；需要恢复旧阅读时，使用升级前阅读投影与对应旧sidecar快照，保留新数据等待再次升级，不能降级后批量重评。
