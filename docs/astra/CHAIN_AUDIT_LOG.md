# 主链路审计日志（astra_chain_audit@1.0.0）

工作台在实盘观察期间，把主链路"看到了什么、做了什么"写成一份规范、紧凑、带哈希链的日志。它用来：

- 事后复盘某个时刻的决策依据（现价、空间门、四要素、两侧候选、门的原因、复核与锁定）；
- 交给模型做审计或归因（每个文件开头自带中文字段说明，可以单独交付）；
- 在主链路迭代前后做对照（同一套统计口径比较两个时间窗口）。

日志只从工作台读视图生成：不发网络请求、不调用模型、不写其他存储，写入失败也不影响工作台。

## 存放与保留

| 文件 | 内容 | 保留 |
|---|---|---|
| `<状态目录>/chain_audit/chain-YYYYMMDD.jsonl` | 按北京时间分日：周期快照（默认每 15 分钟）+ 事件 | 默认 30 天，自动清理 |
| `<状态目录>/chain_audit/chain-daily.jsonl` | 每天北京时间 23:00 一条完整快照 | 长期保留 |

EU 服务器上的状态目录是 `/var/lib/xxproject/workbench`。配置项（环境变量）：

- `ASTRA_CHAIN_AUDIT_ENABLED`（默认 `1`）
- `ASTRA_CHAIN_AUDIT_INTERVAL_MS`（默认 `900000`，最短 60000）
- `ASTRA_CHAIN_AUDIT_RETENTION_DAYS`（默认 `30`）

一条周期快照约 6–8 KB，一天约 0.6 MB，30 天约 20 MB。

## 记录类型

| kind | 何时写 | 内容 |
|---|---|---|
| `header` | 每个文件第一行 | 结构版本、中文字段说明 `field_guide_cn` |
| `periodic` | 每个 15 分钟时段的第一轮刷新 | 完整快照（见下） |
| `daily` | 北京时间 23 点的第一轮刷新 | 与 periodic 相同，写入 `chain-daily.jsonl` |
| `space_gate_transition` | 空间门状态变化 | 从/到、原因码、锚点评分、现价 |
| `review` / `review_rejected` | 模型复核请求完成 / 被拒 | 候选、用途、状态、模型调用次数、适配判断、协议、拒绝原因 |
| `lock` / `lock_rejected` | 锁定或重新追踪 | 追踪 id、是否新建、是否为新参照、来源追踪 |
| `lock_stop` / `lock_stop_rejected` | 停止追踪 | 追踪 id、状态 |

未登录或来源校验失败的请求（401/403）不记录，避免日志被无关请求填满。

## 快照字段（periodic / daily）

| 字段 | 含义 |
|---|---|
| `versions` | FMZ 生产端版本、生产端 schema、读视图 schema、发布清单 id 与哈希、复核提示词与响应协议版本 |
| `market` | 现价、FMZ 事实状态与年龄、事实缺口原因 |
| `space_gate` | 状态、是否放行、原因码、锚点评分与状态、净 Gamma、Gamma 体制、当前状态起点 |
| `elements` | 四要素：TMV 24h/48h、15 分钟 M-DIE（含路径效率、同向占比）、主动成交 4h/12h（CVD、价格涨跌、覆盖小时、是否就绪）、宏观体制与得分 |
| `background` | 资金费率、永续 OI 24h 变化、ETF 近 3 日净流、链上成本价、ATM IV 与 IV 分位、四类背景的用途状态 |
| `sources_not_ok` | 持续采集但当前不正常的来源（按需记录的 Deribit 报价与本机不采集的产品不计入） |
| `candidates` | 每侧：合约、短腿 Delta、现价、短腿与盈亏平衡距离（按边界价的百分比，正值在责任区外）、信用与扣费后净信用、费用及口径、μ（无生产来源时为 null）、快照状态、生产复核门原因、观察复核是否可用、模型解释摘要（类型、状态、适配判断、回执、模型、协议、用途）、程序两问摘要 |
| `locks` | 每条锁定追踪：id、合约、状态、点数、缺口数、最近缺口原因、最近观察时间、停止原因 |
| `llm` | 今日复核额度与是否有复核进行中 |
| `gaps` | 读视图的整体缺口 |

## 完整性：哈希链

每条记录带 `seq`、`prev_hash`、`record_hash`。`record_hash = sha256(去掉 record_hash 后按键排序的紧凑 JSON)`，`prev_hash` 指向同一文件的上一条，文件头的 `prev_hash` 为 null。任何一行被改动、删除或插入，校验都会在那一行失败。

## 获取

- 工作台页面"数据与审计记录"里列出最近的文件、记录数、事件数、哈希链状态，可直接打开。
- 接口：`GET /api/workbench/chain-audit`（索引），`GET /api/workbench/chain-audit/<文件名>`（JSONL 原文）。
- 服务器上直接读取上面的目录。

## 命令行工具（只读）

```bash
python tools/astra_chain_audit_v1.py verify chain-20261012.jsonl
python tools/astra_chain_audit_v1.py summarize chain-20261010.jsonl chain-20261011.jsonl
python tools/astra_chain_audit_v1.py compare --a chain-202610{05..11}.jsonl --b chain-202610{12..18}.jsonl
```

`summarize` 给出窗口内的统计：快照数、空间门放行占比与原因分布、锚点评分分布、事实当前占比、主动成交就绪占比、来源异常占比，以及每侧的短腿距离、盈亏平衡距离、Delta、扣费后净信用（美元）分布，生产复核门打开的占比，各类事件计数和出现过的版本组合。`compare` 把两个窗口的同名统计并排列出。

## 交给模型审计

把一个或几个日文件（含文件头）直接交给模型，再附上类似下面的要求：

> 这是中性回路承保工作台的主链路审计日志，字段含义见每个文件第一行的 field_guide_cn。请只依据日志内容回答：
> 1. 这段时间空间门为什么一直关闭或开启，主要原因码如何变化；
> 2. 两侧候选的短腿距离、盈亏平衡距离与净信用如何分布，有没有异常值；
> 3. 每次复核、锁定、停止发生时的市场与门状态；
> 4. 数据来源与事实状态有哪些缺口，持续多久。
> 不要推断日志里没有的数值；引用时写出记录的 bjt 时间。

## 迭代对照的做法

1. 迭代前，确定基线窗口（例如上线前 7 天）的日文件，用 `summarize` 存一份结果。
2. 迭代上线后，`versions` 字段会出现新的版本组合；取同样长度的窗口再 `summarize`。
3. 用 `compare` 并排看两个窗口；如需细看，筛出 `versions` 不同的记录逐条对照。
4. 日文件默认只保留 30 天，需要更长基线时，在清理前把文件另存，或依赖长期保留的 `chain-daily.jsonl`。

## 不包含的内容

- 不含原始证据正文、WPEM 证明与完整模型回执；需要时按记录里的快照 id 和回执 id 去对应接口取。
- 不含锁定追踪的逐点序列；逐点序列在 `GET /api/workbench/locked-candidates/<id>/series`。
- 不是成交记录：工作台不下单，日志里没有任何实际成交或持仓。
