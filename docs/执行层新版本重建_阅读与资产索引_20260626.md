## 3. 最应该复用的代码资产

### 3.1 运行主链与安全边界

- `demo/execution_build/realsrc/src/strategy.py`
  当前 `run_cycle` 主链、计划/锁定/预提交/持仓管理分支都在这里。新版本可以重构它，但要先读懂现有状态机和安全门。

- `demo/execution_build/realsrc/src/config.py`
  版本号、交易门、风险阈值和默认空跑边界。任何新版本都应保留 `DRY_RUN_PASSED=False` live-readiness 硬门语义。

- `demo/execution_build/realsrc/src/gates.py`
  entry/exit/hedge/kill/emergency 门控拆分资产。适合作为新版本安全层基座。

- `demo/execution_build/realsrc/src/cmd_router.py`
  FMZ `GetCommand` 命令路由、幂等和操作命令入口。新版本可改交互形态，但命令幂等思想应保留。

- `demo/execution_build/realsrc/src/display.py`
  状态栏/诊断表渲染。新版本如果重做 UI，也应复用“中文语义诊断 + 原始 gate id 可追踪”的思路。

### 3.2 信号接收与血缘

- `demo/execution_build/realsrc/src/signal_receiver.py`
  当前 `signal_review.jsonl` 接收、FILE/G 方向权威、未来 `EntryCandidatePackage + SignalContextUpdate` 双包兼容、context 血缘 fail-closed 都在这里。

- `docs/信号执行闭环_L1暂停点_20260624.md`
  信号层和执行层整合边界的历史设计。新版本可参考，但要以当前代码和用户最新大方向为准。

### 3.3 计划、腿选择、VRP 与可行性

- `demo/execution_build/realsrc/src/recommend.py`
  推荐库、候选方案、确认码质量血缘、执行可行性过滤/排序的核心资产。

- `demo/execution_build/realsrc/src/leg_selection.py`
  垂直价差腿选择逻辑。若新版本仍是期权结构执行，可优先复用。

- `demo/execution_build/realsrc/src/plans.py`
  plan/hash/snapshot 相关结构。新版本做审批血缘时应重点参考。

- `demo/execution_build/realsrc/src/vrp_gate.py`
  VRP 定价门。当前缺真实 IV/RV `market_context` 时 fail-closed，不得伪造通过。

- `demo/execution_build/realsrc/src/execution_feasibility.py`
  执行可行性评分、点差/信用保留率/硬门失败项等资产。后续若讨论软门控，先从这里建模。

### 3.4 授权、预提交与账本

- `demo/execution_build/realsrc/src/authorization.py`
  短确认码、风险退出授权、撤销授权等审批资产。

- `demo/execution_build/realsrc/src/ledger.py`

### 3.5 开仓、持仓、风险和对冲

- `demo/execution_build/realsrc/src/execution.py`
  entry/exit/hedge/protection recovery 执行器。新版本若重写订单状态机，也应先读执行器当前约束。

- `demo/execution_build/realsrc/src/position.py`

## 4. 测试资产优先级

首要入口：

- `demo/execution_build/realsrc/tests/run_all.py`

重建新版本时最该先保住的测试族：

- `test_config.py`：安全配置和 live-readiness 门。
- `test_signal_receiver.py`：FILE/G、双包、血缘、TTL、fail-closed。
- `test_recommend.py`、`test_leg_selection.py`、`test_plans.py`：计划与方案库。
- `test_precommit.py`、`test_vrp_gate.py`、`test_execution_feasibility.py`：预提交、VRP、执行可行性。
- `test_authorization.py`、`test_cmd_router.py`、`test_gates.py`、`test_display.py`：交互/授权/展示。
- `test_run_cycle.py`、`test_integration_dryrun.py`、`test_integrated_flow.py`：主链集成。
- `test_position.py`、`test_risk_controls.py`、`test_hedge_risk.py`、`test_hedge.py`、`test_recovery.py`：持仓、风险、对冲和恢复。
- `test_execution.py`、`test_deribit_io.py`、`test_binance_io.py`：执行器与适配层。

新版本不要先删测试。更好的路径是先让旧测试标出哪些资产被保留、哪些行为被有意替换，再建立新测试矩阵。

## 6. 推荐的新版本重建流程

1. 先读本索引和 §1 必读文档，确认 v2.9.9 不是继续推进线，而是资产库。
2. 输出新版本目标：交易结构、信号关系、门控软硬分层、持仓闭环范围、FMZ 交互范围。
3. 列出资产取舍：保留、改造、废弃、待验证四类。
4. 先重建契约和测试，再迁移业务逻辑。尤其是信号包、计划审批、预提交、订单状态机和持仓快照。
5. 保持默认空跑：新版本第一阶段只做本地模拟和展示，不开启真实交易门。
6. 通过 `tests/run_all.py`、`build_bundle.py --check`、`py_compile` 后，再交 Claude 复核。
7. Claude 复核通过后，才进入 FMZ 真机只读/空跑验收；验收前不得写 `DRY_RUN_PASSED=True`。
