## 2. FMZ 交互配置核对

本轮初始问题不是交易所 API，而是 FMZ 策略交互项未在机器人页可用。已在策略页手工补齐并保存以下 7 项：

| 交互名 | 类型 | 说明 |
|---|---|---|
| `拒绝` | 按钮(button) | 放弃当前待批方案 |
| `执行` | 字符串(string) | 输入方案确认码 |
| `授权止盈` | 字符串(string) | 输入持仓授权码 |
| `撤销授权` | 按钮(button) | 撤销止盈授权 |
| `风险退出授权` | 字符串(string) | 输入风险退出授权码 |
| `急停` | 按钮(button) | 停新风险并撤开仓单 |
| `恢复` | 按钮(button) | 清急停并重新等待硬授权 |

实测注意点：

- FMZ 保存策略后会提示“绑定策略已更新，重启实盘生效”，必须重启机器人后再测试 `GetCommand()`。
- 机器人页的交互按钮不在“状态信息”表里，而在独立的折叠面板“策略交互”里；需要展开该面板。
- FMZ 页面“交易平台”区域里普通下拉显示不等于已添加交易所；已添加交易所以红色标签显示。本次只按红色 Deribit 标签作为有效交易所依据。
- 每次发送交互命令后，FMZ 会弹出“指令 xxx 已发送 / 知道了”提示。继续点下一条命令前，应先点“知道了”，再等待 1-2 个 `run_cycle` 周期。

## 4. 返修项

### R1：状态栏缺少命令结果行

现状：

- `run_cycle()` 已写入 `ctx["last_command"]` 和 `ctx["last_command_outcome"]`。
- 但 `disp_console_table()` 没有显示这两个字段。
- 因此错误码 `执行:ZZZZ` 的结果只能从“状态没有改变”间接判断，不能在状态栏直接看到 `confirm_code_invalid_or_stale`。

建议：

- 在“交互控制台”增加一行：`最近命令`。
- 展示内容建议为：`<action> / <status> / <outcome>`。
- 对授权码、确认码等参数不要原文落日志；只显示命令类型和处理结果。

优先级：P0。A2 验收要求“人工批准/拒绝/授权全部进命令账本可追溯”，当前可追溯性在 `_G` 账本里，但操作者界面不可见。

### R2：命令发送成功提示与状态生效存在滞后，文档需写明等待规则

现状：

- `急停` 发送后约一个或多个轮询周期才进入 `KILLED`。
- `恢复`、`拒绝` 也需要关闭 FMZ 的“已发送”提示并等待状态刷新。

建议：

- 在空跑 runbook 中明确：发送命令后先点“知道了”，再等待至少 15-25 秒，直到状态表或日志出现目标状态。
- 不要在“已发送”弹窗未关闭时连续点下一条命令。

优先级：P1。属于操作指引缺口，但不影响代码安全。

### R3：交互配置没有随单文件自动落到 FMZ

现状：

- 单文件代码本身没有让 FMZ 自动创建“策略交互”项。
- 新建策略后如果不手动配置 7 项，机器人能运行，但不会出现可用按钮/字符串输入。
- 因此“当前交付物部署到 FMZ 后，需要手动配置策略交互接口才可正常使用”这一判断成立。这里的“正常使用”特指可操作 `GetCommand()` 人工硬批准、急停、恢复、拒绝等链路；不是指交易所 API 已失败。

建议：

- 短期在 `demo/最新交付物/README.md`、空跑 runbook 和整合 PDF 指引中加入完整 FMZ 配置截图/表格。
- 如 FMZ 支持策略交互元数据导入，应补一个可复制的配置清单；若不支持，明确标注“手工必配”。
- 机器人启动时无法可靠检测 FMZ 是否配置交互项，但文档要把“保存策略后必须重启机器人”作为强制步骤。
- 中期按 R6 收束交互面，避免新部署者被 7 个交互项误导为需要逐步人工操作完整生命周期。

优先级：P0。否则新部署者会误以为策略运行失败。

### R4：命令解析应兼容中文全角冒号

现状：

- FMZ 字符串交互实测生成 `执行:IWJS`，是 ASCII 冒号，当前解析正常。
- 但若操作者手动输入 `执行：IWJS`，`parse_command()` 只按 ASCII `:` 分割，会把整串当命令名并落入 `UNKNOWN`。

建议：

- 在 `parse_command(raw)` 中先把第一个 `：` 规范化为 `:`。
- 同时保留原始 `raw`，便于审计。

优先级：P2。不是本轮 FMZ UI 的实际故障，但属于低成本鲁棒性修复。

### R5：A2 尚未完整封为 `DRY_RUN_PASSED`

本轮已覆盖：交互项可见、重启生效、急停/恢复、错误码拒绝、正确码锁定、OFFLINE 预提交 fail-closed、拒绝清理。

仍需补测：

- 同一确认码重复 `执行` 的 `duplicate_ignored` 可见性。
- 命令账本 `_G` 记录内容的人工可核验路径。
- Gate-A 提交合法性：有效 tick、数量合法化、能开不能关自检。
- “无真实下单”最好补一个交易所订单/成交/持仓只读核对，而不仅是从门控和日志推断。
- FILE/G + `market_context` 的 A3 链路。

### R6：主流程交互面应收束为“一次新增风险硬授权”

现状：

- 当时 FMZ 交互面需要配置 7 项：`拒绝`、`执行`、`授权止盈`、`撤销授权`、`风险退出授权`、`急停`、`恢复`。
- 从执行层语义看，真正的新增风险硬批准只有 `执行:确认码`。`授权止盈`、`风险退出授权` 属于降险授权，`急停`、`恢复`、`拒绝`、`撤销授权` 属于安全覆盖或运维动作。
- 小额实盘配置已定义“一次开仓批准 = 同时授权退出边界”，且 v2.10 起开仓批准会自动捆绑降险授权。因此让操作者在计划确认之后再逐项确认止盈、风险退出、对冲管理和退出，会把执行层职责错误地退回成人工逐步放行。

建议目标：

- 主流程按“每一轮新增风险一次硬授权”设计：计划轮输出确认码，操作者只输入一次 `执行:方案确认码`，执行层锁定方案并进入执行轮。
- 该次授权只覆盖当前方案和当前持仓生命周期，不授权后续新计划。退出、归档或放弃后，系统回到下一轮 `HARD_APPROVAL_WAIT`，等待新的计划确认码。
- 执行轮内由执行层自动处理：开仓尝试、订单管理、止盈、风险退出、对冲减仓、孤儿清理、到期/结束归档。小额阶段对冲开仓仍受 `ALLOW_HEDGE_OPEN=False` 等门控约束，不能因交互收束而自动放大风险。
- `授权止盈`、`风险退出授权`、`撤销授权` 不应作为日常必点步骤。若保留，应降级为高级/应急覆盖，并在状态栏清楚显示其影响，例如“自动退出授权已撤销，禁止新的执行授权”。
- `急停` 必须保留为安全覆盖能力；`恢复` 应保留或由“重新对账并等待新计划硬批准”的等价流程替代。它们不属于正常交易主流程，但不能从系统能力中删除。
- `拒绝` 可降级为“清除当前计划/放弃锁定”的运维动作，或由 TTL 自动过期替代；不应与新增风险授权并列成为操作者每天必走步骤。

返修验收口径：

- 文档和整合 PDF 中把“日常交互”明确写成：`执行:方案确认码` 一项；安全覆盖另列为 `急停`、`恢复/重新对账`、可选 `清除当前计划`。
- 状态栏必须展示“本轮授权边界”：方案编号/确认码脱敏、授权 TTL、止盈边界、风险退出预算、对冲 reduce-only 边界、当前是否允许自动退出。
- A2/A3 后续空跑验收应证明：正确 `执行:确认码` 后，不需要再输入 `授权止盈` 或 `风险退出授权`，系统也能在无真实下单或小额实盘边界内完成降险路径演练。
- 如果最终仍保留二次“允许止盈”交互，必须说明它是监管/风控策略要求，而不是执行层技术必需；默认推荐改为开仓授权同时允许预设边界内止盈和风险退出。

优先级：P0。交互契约不收束，会持续制造部署误解，并削弱“执行层自动管理、自动降险”的核心边界。

## 5. 当前最终状态

测试结束后已用 `拒绝` 清理锁定方案，机器人回到：

- `RUN_CYCLE:HARD_APPROVAL_WAIT`
- 阶段：`待计划硬授权`
- 交易门控：`进场✗ 退出✗ 对冲开✗ 对冲减✗`
- 信号接收：`OFFLINE_MANUAL`

结论：本轮 FMZ 真机空跑证明核心 `GetCommand()` 交互链可工作，且默认安全边界有效；但交互配置文档、命令结果可观测性、命令账本可核验路径必须返修后，才能把 A2 关口标记为完整通过。

## 7. 界面体感收束确认（v2.15.0）

经核（`is_authorized` 不校验 policy + `_grant_bundled_derisk_auth` 在 commit 时建 RISK_EXIT 授权绑定持仓）：**开仓批准后 `authorized=True`，止盈与风险退出退出活动均自动放行**，止盈预算取自入场快照 `max_total_exit_spend`、风险退出预算取自捆绑授权 `max_exit_spend`。故 `授权止盈`/`风险退出授权` 在正常生命周期**已无需手工点**，纯为「自动退出被【撤销授权】后需手工恢复」的应急覆盖。

落地后界面体感：**日常唯一操作 = `执行:方案确认码`**（→自动锁定→预提交→进场门开则开仓→自动管理止盈/风险退出/对冲/到期归档）。`急停`/`恢复` 为安全覆盖，`授权止盈`/`风险退出授权`/`撤销授权`/`拒绝` 为应急/运维覆盖，正常流程不点。具体配置见 `docs/执行层_空跑验证流程.md`「FMZ 交互配置」节。

> **v2.16.0 进一步收束（已被《交互收束交付单》§9 覆盖落地）**：用户明确 FMZ 不适合频繁交互，前端**只保留 `执行` 一项**——`急停/恢复/拒绝/授权止盈/风险退出授权/撤销授权` 全部从前端下线（输入即「未知命令」）；急停=配置门 `KILL_NEW_RISK`、放弃/恢复=批准 TTL 过期 + 重启。本节「应急/运维覆盖按钮」表述以 v2.16 口径为准（不再作为前端按钮存在）。

### 9.4 新增/保留返修意见

1. **R1 需重开或降为“部分通过”**：`最近命令` 行在 `急停` 路径可见，但在错误确认码 `执行:BAD1`、有效确认码 `执行:KLHS`、`恢复` 路径未稳定显示。验收口径应改为：所有 `GetCommand()` 分支都必须在状态栏显示脱敏后的 `<命令类型> -> <处理结果>`，尤其是 `confirm_code_invalid_or_stale`、`plan_locked/precommit_failed`、`recover_to_wait`。
2. **输入框残留需处理**：`执行` 输入框会保留上次填写的确认码，复测中 `KLHS` 残留在输入框内。建议命令发送成功后清空字符串输入框，或在状态栏提示「上一输入已发送，不代表当前选择」。
3. **恢复延迟需要 UI 化**：`恢复` 已能生效，但等待窗口接近 25 秒。建议 `KILLED` 状态下收到恢复命令后先显示 `最近命令 RECOVER -> pending_reconcile`，回到 `HARD_APPROVAL_WAIT` 后再显示 `RECOVER -> recovered_to_hard_wait`。
4. **R5 仍不可封 `DRY_RUN_PASSED`**：本轮尚未完成 duplicate_ignored、命令账本 `_G` 人工核验、交易所只读订单/持仓核对、A3 FILE/G 链路。当前只能判定「新实盘主交互与状态前端基本跑通」，不能封完整 A2。
