# 执行层 FMZ 空跑本轮返修审核与交互收束交付单（2026-06-23）

> 面向对象：后续接手执行层返修的工作 agent。
> 来源：本轮 Chrome/FMZ 真机空跑复测 + 用户补充交互收束意见。
> 目标：把当前“7 个 FMZ 交互项 + 高频日志刷屏”的执行层交互，收束为“一个确认码输入 + 一个执行动作”的计划层到执行层授权入口。

## 0. 先读结论

本轮不是继续优化 7 个交互按钮，而是要改变交互契约：

- **FMZ 前端只保留一个交互：`执行`。**
- `执行` 是字符串输入项，操作者只粘贴计划层给出的确认码，然后点击执行。
- 删除常驻的 `急停`、`恢复`、`拒绝`、`授权止盈`、`风险退出授权`、`撤销授权` 等 FMZ 前端按钮/命令入口。
- 止盈、风险退出、订单管理、到期/退出归档应在确认码授权成功后由执行层自动处理。
- 日志只记录关键事件，不再每几秒刷 `RUN_CYCLE:*` 这类无状态变化日志。
- 状态栏负责展示当前流程状态；日志负责记录事件历史；二者不要互相替代。

这份口径**覆盖**此前“日常只用执行，但保留急停/恢复/拒绝/授权止盈等安全或应急按钮”的折中方案。用户明确要求：FMZ 不适合频繁交互，其前端交互只承担计划轮到执行轮的一次确认码授权。

## 1. 当前真机复测事实

复测对象为用户重新复制最新交付物后，在 FMZ 新建并运行的「中性回路执行层测试」实盘。复测边界为：

- 信号源：`OFFLINE_MANUAL`
- 进场门控：`ALLOW_ENTRY=False`
- 交易门控整体保持空跑/安全关闭
- 策略启动日志显示版本：`S:PM 垂直价差执行链 v2.15.0`

### 1.1 交互项现状

当前 FMZ 仍需要手动配置并展示 7 项交互：

| 当前交互项 | 类型/意图 | 本轮新口径 |
|---|---|---|
| `执行` | 输入方案确认码，推进计划到执行 | 保留，作为唯一 FMZ 交互 |
| `急停` | 停新风险 | 从 FMZ 常驻前端删除，不作为操作者日常按钮 |
| `恢复` | 清急停并重新等待硬授权 | 从 FMZ 常驻前端删除，不作为操作者日常按钮 |
| `拒绝` | 放弃当前待批方案 | 删除或改为内部 TTL/状态过期机制 |
| `授权止盈` | 手工授权止盈 | 删除；止盈应随确认码授权默认允许 |
| `风险退出授权` | 手工授权风险退出 | 删除；风险退出应随确认码授权默认允许 |
| `撤销授权` | 撤销自动退出授权 | 删除常驻入口，避免制造人工逐项放行误解 |

### 1.2 已跑通的行为

| 操作 | 观察 | 结论 |
|---|---|---|
| `执行:KLHS` | 状态进入 `RUN_CYCLE:PLAN_LOCKED`；阶段为「方案锁定·预提交」；显示 `PRECOMMIT_FAILED:vrp_rechecked`；腿位仍为 `短 —@— / 保 —@—` | 正确确认码可被消费并锁定方案；空跑边界下未进入真实下单 |
| `急停` | 状态进入 `RUN_CYCLE:KILLED`，并显示 `最近命令 KILL → killed_new_risk` | 旧安全按钮链路可用，但新口径要求不再暴露为 FMZ 常驻交互 |
| `恢复` | 约 25 秒后回到 `RUN_CYCLE:HARD_APPROVAL_WAIT` | 旧恢复链路可用，但延迟较长，且新口径要求不再作为前端常驻按钮 |
| `执行:BAD1` | 状态保持 `RUN_CYCLE:HARD_APPROVAL_WAIT` | 错误码未推进执行，安全性通过 |

### 1.3 明确问题

1. **交互面仍过重**
   7 个按钮/输入项会让操作者误以为执行层需要人工逐项确认、急停、恢复、授权止盈、授权风险退出。用户要求改为一个确认码输入和一个执行动作。

2. **确认码反馈不足**
   错误确认码 `BAD1` 被安全拒绝，但状态栏和日志没有明确显示“确认码无效/过期/不匹配”。不能只靠“状态没变化”判断拒绝成功。

3. **日志刷屏严重**
   FMZ 日志中存在大量重复的 `RUN_CYCLE:HARD_APPROVAL_WAIT`、`RUN_CYCLE:PLAN_LOCKED` 等周期性状态日志。FMZ 不适合做高频状态交互，这会淹没真正关键事件。

4. **状态栏与日志职责混淆**
   当前状态栏能展示流程状态，但日志也在高频重复状态。目标应是：状态栏展示当前态，日志只记录事件态。

## 2. 新交互契约

### 2.1 唯一 FMZ 交互

最终 FMZ 策略交互只配置一项：

| 名称 | 类型 | 描述 |
|---|---|---|
| `执行` | 字符串输入 | 输入计划层输出的方案确认码，点击执行后进入执行层流程 |

操作者流程：

1. 在状态栏查看待批方案明细。
2. 复制选中方案的确认码。
3. 粘贴到 `执行` 输入框。
4. 点击 `执行`。
5. 查看状态栏和事件日志反馈。

### 2.2 执行授权语义

`执行:确认码` 成功后，授权语义为：

- 只授权当前方案。
- 只覆盖当前方案/当前持仓生命周期。
- 不授权后续新计划。
- 退出、归档、失败或过期后，必须回到下一轮 `HARD_APPROVAL_WAIT`，等待新的计划层确认码。

该授权应覆盖当前方案生命周期内的执行层自动管理：

- 开仓尝试
- 订单管理
- 止盈
- 风险退出
- 必要的降险退出
- 对冲减仓或 reduce-only 边界内动作
- 到期/退出后归档

如果交易门控仍关闭，应继续 fail-closed；交互收束不等于放大交易权限。

### 2.3 止盈默认执行

`授权止盈` 不再作为 FMZ 交互项存在。确认码授权成功后，止盈和风险退出应在预设预算/边界内默认允许执行。

状态栏应显示授权边界，例如：

- 当前方案编号
- 确认码脱敏标识
- 授权 TTL 或过期条件
- 止盈预算/边界
- 风险退出预算/边界
- 对冲或 reduce-only 边界
- 当前是否允许自动退出

## 3. 代码层改造要求

### 3.1 删除或废弃多余命令入口

从 FMZ 交付物的可交互命令面中移除：

- `急停`
- `恢复`
- `拒绝`
- `授权止盈`
- `风险退出授权`
- `撤销授权`

实现上至少应做到：

- 文档不再要求配置这些 FMZ 交互项。
- `COMMAND_ALIASES`、`parse_command`、`GetCommand()` 分支、状态栏提示、README/runbook 中不再把这些命令作为前端交互暴露。
- 如果某些内部安全机制仍需要保留，不应以 FMZ 常驻按钮形式出现；应改为配置门控、状态机 fail-closed、TTL 过期、重启后重新等待确认码等内部机制。

### 3.2 收束 `执行` 命令处理

`执行` 命令应成为唯一人工入口，并覆盖以下结果分支：

| 输入情况 | 状态行为 | 日志/状态栏反馈 |
|---|---|---|
| 空确认码 | 保持 `HARD_APPROVAL_WAIT` | `执行失败：确认码为空` |
| 确认码格式错误 | 保持 `HARD_APPROVAL_WAIT` | `执行失败：确认码格式无效` |
| 确认码不存在/过期/不匹配 | 保持 `HARD_APPROVAL_WAIT` | `执行失败：确认码无效或已过期` |
| 确认码正确 | 锁定当前方案，进入执行层流程 | `执行通过：方案已锁定` |
| 预提交失败 | 保持 fail-closed，不下单 | 显示具体原因，例如 `vrp_rechecked` |
| 交易门控关闭 | 不下单 | 显示 `进场门控关闭，未真实下单` |

反馈必须同时满足：

- 状态栏可见。
- 日志有一条关键事件记录。
- 确认码本体不在日志中明文泄露，可显示脱敏标识或方案编号。

### 3.3 删除无效日志刷屏

删除或显著降频以下无信息量日志：

- 每轮重复输出 `RUN_CYCLE:HARD_APPROVAL_WAIT`
- 每轮重复输出 `RUN_CYCLE:PLAN_LOCKED`
- 每轮重复输出腿位为空的 `短 —@— / 保 —@— / 释放 —`

日志只保留关键事件：

| 事件 | 是否写日志 |
|---|---|
| 策略启动 | 是 |
| 新一轮待批方案生成或方案内容变化 | 是 |
| 收到 `执行` 命令 | 是，脱敏 |
| 确认码错误 | 是 |
| 确认码正确并锁定方案 | 是 |
| 预提交通过/失败 | 是 |
| 交易门控阻断真实下单 | 是 |
| 进入执行层关键阶段 | 是 |
| 退出、归档、回到下一轮等待 | 是 |
| 无状态变化的周期轮询 | 否 |

### 3.4 状态栏展示要求

状态栏不是日志替代品。它应始终展示当前可操作态：

在 `HARD_APPROVAL_WAIT`：

- 当前阶段：待计划硬授权
- 当前交易门控
- 信号源
- 待批方案明细
- 每个方案确认码
- 操作提示：只输入确认码并点击 `执行`

在确认码正确后：

- 当前阶段：方案锁定/预提交/执行中
- 方案编号
- 授权边界
- 预提交结果
- 是否真实下单、为何未下单
- 后续是否需要人工动作：正常情况下应为“无需继续操作”

在确认码错误后：

- 当前阶段仍为待计划硬授权
- 最近执行结果：确认码无效/过期/不匹配
- 不应推进到锁定或预提交

## 5. 验收标准

返修完成后，工作 agent 至少要跑通以下检查：

### 5.1 静态检查

- 交付物中不再提示配置 7 个 FMZ 交互项。
- 文档中最终配置表只保留 `执行`。
- 状态栏操作提示不再出现“急停/恢复/授权止盈/风险退出授权/撤销授权”为日常按钮。
- 日志刷屏代码被删除或有明确的状态变化去重。

### 5.2 FMZ 真机空跑检查

在 `OFFLINE_MANUAL` + 交易门控关闭条件下：

1. FMZ 交互面板只出现 `执行`。
2. 输入错误确认码，状态保持 `HARD_APPROVAL_WAIT`，状态栏和日志显示明确拒绝原因。
3. 输入正确确认码，状态进入方案锁定/执行层流程，状态栏和日志显示确认通过。
4. 不需要再点击 `授权止盈` 或任何二次授权按钮。
5. 预提交或交易门控阻断时，日志记录具体原因，且没有真实下单。
6. 无状态变化时，日志不再持续刷屏。
7. 退出、归档或失败后，策略回到下一轮 `HARD_APPROVAL_WAIT`。

### 5.3 不可封关项

以下事项未完成前，不能标记 `DRY_RUN_PASSED`：

- 错误确认码拒绝原因可见。
- 正确确认码执行反馈可见。
- 日志刷屏已清理。
- FMZ 交互只剩 `执行`。
- 交易所订单/成交/持仓完成只读核对，证明无真实下单或无新仓。
- A3 FILE/G + `market_context` 链路另行跑通。

## 6. 给接手 agent 的实现顺序建议

建议按以下顺序处理，避免边改边混淆边界：

1. **先改交互契约**：只保留 `执行`，移除其它 FMZ 前端命令入口和文档配置。
2. **再改命令反馈**：补齐错误码、正确码、预提交失败、门控阻断的状态栏与日志反馈。
3. **再删日志刷屏**：把周期状态日志改成状态变化/事件日志。
4. **最后更新文档/PDF**：把 runbook、小额实盘配置、整合全量指引统一到“一码一执行”。
5. **最后做 FMZ 真机复测**：不要只靠本地测试替代 `GetCommand()` 验证。

## 7. 注意事项

- 不要把“删除 FMZ 前端按钮”误解成放宽安全边界。交易门控、fail-closed、预提交复核、风险预算仍必须存在。
- 不要把止盈默认执行误解成无边界止盈。止盈应在确认码授权绑定的当前方案预算和生命周期内执行。
- 不要恢复多按钮配置作为“保险”。用户本轮明确要求 FMZ 前端只保留确认码输入与执行动作。
- 不要用高频日志模拟状态栏。FMZ 日志应沉淀关键事件，而不是每轮刷新当前状态。
- 不要声称 A2 已通过。当前只能说主交互链路和前端展示有复测证据，完整 `DRY_RUN_PASSED` 仍需后续返修和真机复测。
